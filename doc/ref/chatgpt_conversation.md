      │
      ▼
「それめっちゃ分かる！私も似たことあった！」

これだと、**「何をするか」と「どう言うか」を分離**できます。

## 私が今一番ワクワクしている設計

ここまで話していて、一つ「人間っぽさ」をさらに高められそうなアイデアが浮かびました。

**Dialogue Actを1つだけ選ぶのではなく、「会話期待値」を持たせる**んです。

例えば、

```
A「昨日映画見た？」
```

この発話は、相手に「回答してほしい」という期待を作ります。

Conversation Managerは発話ごとに、

```typescript
SpeechExpectation {
    expectedActs: [
        { act: "回答", weight: 0.7 },
        { act: "質問返し", weight: 0.2 },
        { act: "冗談", weight: 0.1 }
    ]
}
```

のような期待値を生成します。

Bは基本的にはこの期待に沿って応答しますが、性格や関係性によって少し外すこともあります。

* 真面目なキャラ → 「回答」を選びやすい
* 天然キャラ → 「冗談」や「脱線」を選びやすい
* 親友同士 → あえて期待を裏切ってボケることも自然

つまり、**前の発話が次の発話の確率分布を作る**わけです。

この設計だと、「突然話題が飛ぶ」「質問を無視する」といった違和感を抑えつつ、適度な意外性も出せます。しかも、この期待値はルールベースで計算できるため、高価なLLMを毎ターン呼ばなくても十分実現可能です。

私なら、まずは **Conversation Managerをルールベースで実装し、LLMは「セリフの表現」と「微妙なニュアンス付け」に集中させる**構成から始めます。その方が、低コストなOSSモデルでも安定した自然な会話エンジンに育てやすいと思います。

depthや重みはどうやって決定しますか？

---

はい。ここはかなり重要です。

結論から言うと、**depthや発話行為の重みをLLMに毎回「0〜100で決めて」と丸投げするのはおすすめしません**。

私なら、

> **基本値はルール・状態から計算 → LLMは「意味の解釈」が必要な部分だけ担当 → 実際の会話ログからパラメータを調整**

という3段構成にします。

---

# 1. まず `depth` は「何回掘ったか」ではなく「話題の階層」にする

例えば、

```text
旅行
 └─ 長崎
     └─ ハウステンボス
         └─ ホテル
             └─ 朝食
```

なら、

```text
旅行          depth = 0
長崎          depth = 1
ハウステンボス depth = 2
ホテル        depth = 3
朝食          depth = 4
```

です。

ただし、ここで重要なのは、

**depthそのものを「話題を変える判定」に使わない**

ことです。

例えば、

> A「長崎行ったんだ」
>
> B「うん」
>
> A「ハウステンボス行った？」
>
> B「行った」
>
> A「ホテルどこだった？」
>
> B「ホテルヨーロッパ」

ならdepthは深くなっています。

でも、

> A「ホテルどうだった？」
>
> B「めちゃくちゃ良かったよ」
>
> A「朝食も美味しかった？」
>
> B「うん、クロワッサンがすごく美味しくて」
>
> A「クロワッサン好きなんだよね」
>
> B「そうそう。昔から好き」

これはかなり自然です。

つまり、

**depthが深い = 話題を変える**

ではありません。

---

# 2. `depth` はTopic Treeから機械的に決める

ここはLLMに数値を付けさせる必要はありません。

例えば現在のTopicが

```json
{
  "id": "hotel_breakfast",
  "parent": "hotel",
  "depth": 3
}
```

ならdepthは単純に

```text
parent.depth + 1
```

です。

問題は、

> 「これは同じ話題なのか？新しい話題なのか？」

ですよね。

ここだけLLMまたはEmbeddingを使います。

---

# 3. Topic判定は3段階にするのが良い

新しい発話が来たら、

```text
新しい発話
   │
   ▼
キーワード・Embeddingで既存Topicとの類似度
   │
   ├─ 高い → 同じTopic
   │
   ├─ 中間 → 子Topic候補
   │
   └─ 低い → 新Topic
```

とします。

例えば現在、

```text
Topic = 犬
```

で、

> 「そういえば昔飼ってた犬さ」

なら、

```text
犬
└─ 昔飼っていた犬
```

なので子Topic。

一方、

> 「そういえば最近ゲーム買ったんだけど」

なら

```text
犬

ゲーム ← 新Topic
```

です。

---

# 4. ただしEmbeddingだけでは不十分

ここが面白いところです。

例えば、

> 「昔から犬好きだよな」

と

> 「小学校のとき一緒に犬拾ったよな」

は、文章としては別の話ですが、

**幼馴染というRelationshipでは強く関連しています。**

なのでTopic判定には、

```text
Semantic similarity
+
Relationship memory
+
Conversation context
```

を使いたいです。

つまり、

```text
Topic判定
       │
       ├── 現在の話題との意味的類似度
       │
       ├── キャラクターの記憶との関連度
       │
       └── 二人の共有記憶との関連度
```

です。
