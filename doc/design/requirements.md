# AI会話エンジン 要件定義書

対象参照: `doc/ref/chatgpt_conversation.md`（設計検討の元会話）

## 1. 背景・目的

AIキャラクター同士が会話する動画コンテンツを制作するにあたり、既存のLLM同士の掛け合いは「毎ターンその場で応答する」ため、以下の問題が発生している。

- 話題が深まらない、または不自然に長く同じ話題を掘り続ける
- 質問→回答→質問→回答という「インタビュー」的な単調なリズムになる
- キャラクター同士の関係性（幼馴染・親友・初対面など）が発話内容や言葉遣いに反映されない
- LLMに会話の構成そのものを丸投げすると、コストが高く、かつ挙動が不安定になる

本プロジェクトの目的は、**「LLMに会話を作らせる」のではなく「人間らしい会話を再現するシステム」を作ること**である。会話の構造（何を話すか・どう繋げるか）はルールベース／状態管理で担保し、LLMは「セリフの自然な言語表現」に役割を限定することで、低コストなLLM（OSSモデル含む）でも自然な会話を実現する。

## 2. スコープ

### 2.1 対象とする範囲
- **最大4体のAIキャラクターによる多人数会話を自動生成するエンジン**（2人会話を基礎としつつ、3〜4人会話を最終ゴールとする）
- キャラクターの内部状態（感情・目標・意図・記憶）管理
- キャラクター間の関係性（Relationship）管理と、会話への反映（4体間の全ペア関係を含む）
- 多人数会話における話者選択・発話順・割り込み/相槌の制御
- 会話全体の進行管理（話題管理・テンポ管理・終了判定）
- 発話行為（Dialogue Act）の選択ロジック
- LLMへの最終的なセリフ生成の指示（プロンプト設計を含む）
- **開発・デバッグ用モニタリングUI**（生成中のセリフ、各キャラクター/会話のパラメータ、各レイヤーの計算過程をリアルタイム表示し、かつ後から参照できるログとして表示する画面）

### 2.2 対象外（将来検討事項）
- 音声合成・VRアバター等のフロントエンド表現（本エンジンは会話テキスト生成までを担う）
- 5人以上のさらなる大人数会話（4体を上限として設計するが、それ以上のスケールは将来検討）
- 会話ログからの自動パラメータ学習・MLモデル化（将来フェーズ。初期はルールベース運用）

### 2.3 段階的な実装方針
多人数会話は2人会話より複雑度が高い（話者選択・関係性の組み合わせ爆発・話題の分岐）ため、以下の順で段階的に実装する。

1. **フェーズ1**: 2体会話でCharacter Brain / Relationship Engine / Dialogue Planner / Conversation Managerの基本設計を確立する。
2. **フェーズ2**: 3〜4体に拡張し、話者選択（Speaker Selection）・関係性グラフの多対応・グループ内の話題分岐/合流を追加する。
3. **フェーズ3**: 4体構成でのチューニング・ログ収集・パラメータ調整を行う。

## 3. 全体アーキテクチャ方針

会話生成を以下の5層構造とする。

```
Layer 5: LLM              … セリフ生成（表現のみ）
Layer 4: Character Brain  … 感情・目的・記憶・関係性反映
Layer 3: Dialogue Planner … 発話行為・話題・テンポの決定
Layer 2: Story Manager    … シーン・動画構成
Layer 1: World State      … 世界設定・時間・イベント
```

設計原則:
1. **「何をするか」と「どう言うか」を分離する**。発話行為（Dialogue Act）や話題の決定はルールベースの状態計算で行い、LLMは決定された内容を自然な文章に変換する役割に限定する。
2. **状態は毎ターン更新してから発話を生成する**（会話 → 状態更新 → 発話生成の順序を厳守）。
3. **確率的選択を用いる**。最もスコアが高い選択肢を機械的に選ぶのではなく、Softmax等で確率分布化し、揺らぎのある自然な選択を行う。
4. **関係性は静的設定ではなく、会話を通じて成長する**。共有記憶や信頼度は会話結果によって更新される。

## 4. 機能要件

詳細は `features.md` を参照。主要な機能ドメインは以下の通り。

- キャラクター状態管理（Character Brain）
- 関係性管理（Relationship Engine）
- 会話状態管理（Conversation State / Topic）
- 発話行為選択（Dialogue Planner）
- 記憶管理（Memory：自己記憶・共有記憶、短期・中期・長期）
- セリフ生成（LLM連携）
- 会話進行管理（Conversation Manager：話題転換・終了判定）
- モニタリング／ログUI（リアルタイム可視化とログ閲覧）

## 5. 非機能要件

| 項目 | 要件 |
|---|---|
| コスト | 毎ターンLLMに会話構造全体を推論させない。安価なOSSモデル（Gemma/Qwen等）や小型モデルでの運用を前提とし、トークン消費を抑える設計とする |
| LLMプロバイダ | LLMは **Together AI** を利用する。疎通確認・開発検証時は最も安価なモデル **`google/gemma-3n-E4B-it`** を既定とし、モデルIDは設定で切り替え可能にする（F7.2） |
| 拡張性 | シナリオ（雑談・恋愛相談・コメディ・討論等）を上位レイヤーの差し替えのみで対応できること |
| 一貫性 | 同一状態からの生成結果は完全な決定論である必要はないが、キャラクター設定・関係性・記憶と矛盾する発話を生成しないこと |
| 再現性/デバッグ性 | 各ターンの状態（ConversationState, CharacterState, 選択されたDialogueAct、Score計算内訳）をログとして保持し、不自然な発話の原因を追跡できること |
| チューニング性 | Dialogue Actの重み係数（Base/Personality/Relationship/Topic/Emotion/Context の各Modifier）を外部設定として調整可能にすること |
| 将来のML化 | 会話ログ＋人手評価データを蓄積し、将来的にルールベースの重み計算を統計モデル／小型MLモデルへ置き換え可能な構造にすること |
| 可観測性 | 各ターンで各レイヤー（Topic Analyzer / Relationship Engine / Dialogue Planner / Memory Retriever / LLM）が生成した中間結果を、生成と同時に外部（UI）から参照できる形で出力すること。UIは生成処理をブロックしない（非同期にイベントを流す）こと |
| ログ保存性 | ターンログ（F8.1）はセッション終了後も参照可能な形で永続化され、UI側で過去セッションを検索・再生できること |
| プロンプト保守性 | LLMへ送信するプロンプト（F7.1のセリフ生成プロンプト等）はコードに埋め込まず、テキストファイル（Markdown/プレーンテキスト等）として外部管理すること。変数展開部分（キャラクター名・感情・Dialogue Act・想起記憶等）をテンプレートとして分離し、非エンジニアやプロンプトチューニング担当者でもコード変更なしに文面を編集・差し替えできるようにすること |

## 6. 用語定義

| 用語 | 説明 |
|---|---|
| CharacterState / Character Brain | キャラクター個体が持つ性格・感情・目標・意図・記憶・関係性参照などの内部状態 |
| ConversationState | 現在の会話全体の状態（話題・雰囲気・テンポ・沈黙リスク等） |
| Topic | 会話中の話題単位。親子関係を持つツリー構造で、depth/energy/novelty/unresolvedなどを保持 |
| Dialogue Act（発話行為） | 質問・回答・共感・冗談・話題転換など、発話が果たす機能的役割 |
| Dialogue Planner | ConversationState等からDialogue Actの重みを計算し、確率的に選択するコンポーネント |
| Relationship Engine | キャラクター間の関係タイプ・信頼度・親密度・共有記憶・二人の歴史（Relationship Story）を管理するコンポーネント |
| Shared Memory（共有記憶） | 特定のキャラクター同士が共有する体験の記憶。キーワード検索により会話中に想起される |
| Conversation Manager | 会話全体の進行（話題継続/転換判断、終了判定、発話順）を統括するコンポーネント |
| Speaker Selection（話者選択） | 3人以上の会話において、次にどのキャラクターが発話するかを決定する機能。発話への期待（誰に話を振ったか）、各キャラクターの積極性・関係性、直近の発話頻度の偏りなどから確率的に決定する |

## 7. 成功基準

### 7.1 フェーズ1（2体会話）
- 2キャラクターによる**50ターン程度**の長い雑談を生成した際、単調な「質問→回答」の連続にならず、共感・体験談・冗談・話題転換などのDialogue Actが自然な頻度で混在すること
- 関係性設定（例：幼馴染）が、少なくとも1回以上、共有記憶を参照した発話（例：「昔から犬好きだよな」）として表出すること
- 同一の初期状態から複数回生成しても、発話内容に確率的な揺らぎ（毎回同じ会話にならない）が確認できること
- OSSの小型モデルでもDialogue Act選択・話題管理が破綻しないこと（LLMはセリフ表現のみを担当していることの確認）
- **話題の推移**: 50ターンの間にTopicのlife/energy減衰により、話題転換（新規/派生Topicへの移行）が複数回（目安3回以上）自然に発生すること。1つの話題に50ターン張り付き続けない、または不自然に高頻度で転換し続けないこと
- **記憶・話題の重複回避**: 同一のShared Memoryや同一Topicが、短い間隔で不自然に繰り返し想起・再訪されないこと（Memory Retrieverが直近の想起履歴を考慮すること）
- **後半の破綻がないこと**: 会話後半（30〜50ターン目）でも前半と同様にキャラクター設定・関係性・記憶との矛盾が生じず、状態更新の蓄積によるドリフト（感情や関係性数値が不自然な値に張り付く等）が発生しないこと
- **リズムの持続性**: Rhythm管理（F4.6）により、50ターンを通して「質問→回答」の連続が長期化しないこと（目安として同一パターンの連続を3〜4ターン以内に補正できること）

### 7.2 フェーズ2〜3（最終ゴール：4体会話）
- 4キャラクターによる会話で、特定の1〜2人だけが発話し続ける偏りが生じず、全員に発話機会が分配されること（ただし均等である必要はなく、キャラクター性格・関係性に応じた偏りは許容する）
- ある発話が特定の相手（一人または複数）に向けられていることが自然に表現され、名指し・呼びかけによって次の話者が誘導される場面が生成できること
- 4体の全ペア関係（6組）の関係性が破綻なく管理され、それぞれの関係性に応じた話し方・話題選択の違いが表出すること
- 複数の話題が同時並行的に会話グループ内で分岐・合流する状況（例：2人が別の話題で盛り上がり、後で合流する）に対応できること
